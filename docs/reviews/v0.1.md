# v0.1 review gate

Review of `rnd` at `7278de4` (v0.1, Foundation: #23 to #29) against `docs/SPEC.md` (sections 3.A, 3.6, 3.7, 4, 9 and 12.3) and the rules in `CLAUDE.md`. Reviewed on 2026-10-30 on branch `feature/infra-v0-1-review`. Findings already listed in `docs/reviews/phase-0.md` are not repeated. Their current status is in the table "Phase 0 findings now" below.

## Summary

v0.1 is solid where it matters most: isolation. Row-level security is on every table and is tested directly against PostgreSQL. A request with no user sees nothing. Accounts can only be created through one `SECURITY DEFINER` function that checks the allowlist and the user cap. The API takes the user only from a verified ES256/RS256 token and rejects every client-supplied `user_id` (strict bodies, tested). Another user's plan answers 404. Phase 0's v0.1 blocker (`auth.uid()` grants) is resolved by ADR 010: policies use the schema's own `current_user_id()`, and the PUBLIC stub is gone from the tests.

The review found **two correctness bugs, both fixed with tests**:

- the schedule placed work on days before the plan's start date;
- the first logged hours on an imported task wiped the hours the plan file brought with it.

It also added two guard tests (views and `SECURITY DEFINER` functions in the environment schemas; legal versions against the documents) and fixed three stale doc statements.

There are no open High findings. The open Medium items are:

- no CSP while the Supabase session sits in `localStorage`;
- the sign-in form has no Turnstile or rate limit, and the built-in mailer is limited;
- account deletion leaves the Supabase Auth user, which contradicts the privacy policy (owner decision);
- the health check still does not touch the database, so the free project can pause.

Everything else is Low or setup that only the owner can do (checklist at the end).

All checks pass: `pnpm install --frozen-lockfile && pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm api:types:check`. They ran against a throwaway PostgreSQL 16 cluster with `CI=1`, so no database test was skipped.

Checked and fine:

- RLS is enabled on all 12 tables in both schemas. Every user-owned table has an `app_user` policy keyed by `current_user_id()`, and a query without claims returns 0 rows on each (`data-model.test.ts`).
- `events` and `legal_acceptances` are append-only for the app (privileges and policies). `accepted_at` is set by the database.
- Composite keys `(user_id, id)` and child foreign keys on `(user_id, plan_id)`, so a row cannot attach to another user's plan, and client ids cannot be probed across users.
- `provision_user` and `delete_account`: owner-owned, `search_path` pinned, no PUBLIC execute. `provision_user` is executable only by the login role, and `delete_account` only by the user role. `delete_account` takes no argument.
- JWT verification: ES256/RS256 only, issuer and audience checked, `sub` must be a UUID, keys from JWKS with a 5 s timeout. With no configuration, every token is rejected and DB routes answer 503. `NODE_ENV=production` refuses to start without the auth and DB settings.
- Schema names in SQL come only from the fixed `prod`/`rnd` map (`database.ts:4-17`). Table and column names in SQL are constants. All values are parameters.
- Bodies are strict where it matters (`patchTaskBody`, `logBody`, `updateMeBody`, `deleteMeBody`). Import reads only the plan file fields. Client `user_id` is ignored (tested).
- Error shape: 4xx messages are fixed or safe, and 5xx never exposes details. The guard returns one 403 message for not-allowed, cap-reached and disabled, so the allowlist cannot be probed.
- Idempotency: plan import uses the client plan id with a content hash (409 on different content, concurrent first calls tested). Logs use client ids, and a replay with different data gets 409. Complete, skip and reopen are idempotent. Phase 0 suggestion 9 (an idempotency table) is no longer needed for these endpoints, because each of them is idempotent on its own id.
- The app never marks a task done: logs only set `suggestDone`, and completion is a separate explicit call.
- Dates: `date` columns stay plain strings (`database.ts:63-70`). The web formats dates in UTC from `YYYY-MM-DD`, so the browser zone causes no shift. "Today" is computed in the plan's time zone on the server.
- Legal pages: `marked` renders only the committed drafts, bundled at build time. The drafts contain no raw HTML. Imported task and lesson links are rendered only for `http(s)` (`lib/links.ts`).
- No AI calls exist in v0.1, so no personal data goes to any model. The display name and email stay in the database.
- No secrets: the CI database password is a throwaway for a service container, and `.env.example` files contain names only.

## Spec / data disagreements (not guessed; owner to decide)

1. **What part of 3.A is v0.1.** Section 11 puts "sign-in and accounts with RLS (3.A)" in v0.1. 3.A includes Request access, invites, the capacity page, Turnstile and a per-IP limit on the sign-in form. The implementation defers these to v0.4 (`docs/setup/api-auth.md` "Not built here"). Until then, testers are added by hand to `allowed_emails`. Is that the intended v0.1?
2. **`auth.uid()` in the spec.** 3.A says policies use `auth.uid()` and `set role authenticated`. The code uses `<schema>.current_user_id()` and `app_<schema>_user` (ADR 003 and ADR 010). The spec text is out of date. It is not changed here.
3. **CV-update task.** Spec 3.6 and the acceptance test "Completing a certificate → a CV-update task on the same day" describe a scheduling behaviour. Section 11 puts "automatic CV tasks" in v0.4. Today `complete` writes a `certificate.earned` event and creates no task (`docs/api-plans.md` notes this).
4. **Past days.** "Past days never change" (spec 9) assumes stored schedules. v0.1 computes the schedule on every read (finding 14). Which version should persist blocks?
5. **Plan start date.** The spec does not say whether `Plan.startDate` limits scheduling. Fix 1 treats it as the first day on which work may be placed. If the owner wants "start date is informational only", revert that commit.
6. **Legal acceptance.** 3.A says the user accepts the **Terms** once at sign-up. The app requires both the Terms and the Privacy Policy (`CURRENT_LEGAL_VERSIONS`). This is stricter. Is that intended?
7. **Accessibility checks.** 3.D asks for axe "with Playwright" in CI. v0.1 runs axe in jsdom unit tests (`apps/web/src/test/axe.ts`). jsdom cannot check colour contrast. Playwright is listed for v0.2.
8. **Deletion and backups.** The privacy policy promises deletion from backups within 30 days. Backups live in the private repo with a 30-day retention that has not been set up or verified yet (phase 0 #8).

## Resolved after review

- **Finding 5 (Auth user stays after account deletion): resolved by owner decision, branch `feature/api-delete-auth-user`.** `DELETE /me` now also deletes the Supabase Auth user through the Admin API, using a server-only `SUPABASE_SERVICE_ROLE_KEY` on Render (required in production). The Skillstack rows and the Auth user are removed in one transaction, so an Auth failure rolls everything back (502, retryable). The privacy policy wording is now accurate as written. Details and open checks: `docs/setup/api-auth.md`. The checklist item "Account deletion and the Supabase Auth user" is answered; the owner still has to add the two Render variables.

## Suggestions for v0.2

1. Add a CSP to `vercel.json`, at least `default-src 'self'`, with `connect-src` for the API origin and `https://<ref>.supabase.co`, `frame-ancestors 'none'`, `object-src 'none'` and `base-uri 'none'`, and test it on the R&D preview (finding 3). Add one to the API outside `/api/v1/docs`.
2. Wire Turnstile into `sendCode` and the Google button (the seam exists). Add a per-IP limit on the sign-in path, and set up a free SMTP provider (needs check) before inviting anyone outside the Supabase team (finding 4).
3. Make `/api/v1/health` read `environment_info` as `app_<s>_user`. This proves the role, the schema and RLS, and keeps the project from pausing (finding 6). Keep Render's health path on a check that does not fail the deploy when the database is briefly unavailable, or use a separate `/health/db`.
4. Persist past blocks (or the day's schedule) and pass them as `frozenBlocks`, so that "past days never change" becomes testable (finding 14). Write `schedule.changed` events from one server-side "apply time settings" endpoint that saves the pattern and overrides in one transaction (finding 13).
5. Add per-weekday hours to Time settings (finding 7). Refetch the schedule on focus and at local midnight (finding 8).
6. Check Terms acceptance on the server for the routes the intake will use (finding 9). Constrain `support_access_until` to `now() + 7 days` before the Tier 2 policies (finding 10).
7. Reject NUL in all free-text API fields (finding 11). Log database errors by `code` and `routine` only, without `detail` (finding 12).
8. Strengthen the two weak schedule tests (finding 15): assert the actual anchor warning for a known overload, and fake the clock near midnight to prove `today` follows the plan's zone, not UTC.
9. Carry-overs from Phase 0 that are now cheaper to do than later:
   - pin actions to SHAs;
   - lint in the `web` and `api` jobs;
   - `test-backup.sh` in CI;
   - fail production builds without explicit `VITE_APP_ENV`, `VITE_API_URL` and `APP_ENV`;
   - restrict task and lesson URLs to `https` in the shared schema.
