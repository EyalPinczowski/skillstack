# v0.2 review gate

Review of `rnd` at `c2118f3` (v0.2, Daily experience: #31 to #42) against `docs/SPEC.md` (3.1, 3.2, 3.4, 3.6, the section 9 tests for scheduling, day review, dashboard and briefing, robustness and extensibility, and 12.2/12.3) and the rules in `CLAUDE.md`. Reviewed on 2026-10-31 on branch `feature/infra-v0-2-review`. Findings already in `docs/reviews/phase-0.md` and `docs/reviews/v0.1.md` are not repeated; their status is in "Resolved since v0.1" and "Still open from earlier reviews".

## Summary

v0.2 is careful work. Every new table has RLS with an `app_user` policy keyed by `current_user_id()`, append-only tables are enforced by privileges and by policies, and the `pg_class`-based coverage test fails if a new user-owned table is not in the parametrised RLS tests. There is no new `SECURITY DEFINER` function. Suggestions are recomputed on the server for preview and accept: the client sends only an id and an option number, and an unknown or stale id is refused with 409. The Terms guard is deny-by-default (a new route is blocked unless it is on a four-entry exempt list). NUL characters are refused with 422 on every free-text body. The service key never reaches a log line or a response, and the test-only seams (`VITE_E2E`, `E2E_NOW`) are excluded from production by a build test and a `NODE_ENV` check.

The review found:

- **one High, open (owner decision):** "Delete my account" on R&D deletes the shared Supabase Auth user, which silently orphans the same person's Operational account and data (finding 1);
- **two bugs, both fixed with tests that fail without the fix:** a deadlock between a task edit and a log write on the same task (finding 2), and the day-state advisory lock shared between `prod` and `rnd` (finding 3);
- one spec acceptance test that the code deliberately does not meet as written (a **skipped** task is left out of the weekly "Open tasks", finding 4), and the demo plan does not let the briefing test pass (8 course tasks without a lesson link, finding 5).

Everything else is Medium or Low (table below).

All checks pass: `pnpm install --frozen-lockfile && pnpm format:check && pnpm lint && pnpm typecheck && pnpm test && pnpm api:types:check`, against a throwaway PostgreSQL 16 cluster with `CI=1` (no database test skipped). The Playwright e2e suite (4 tests, the 3 core flows) passed on its own throwaway cluster and ports.

Checked and fine:

- `day_sessions`, `schedule_days`, `day_reviews`, `adjustments`: RLS on, `app_user` policies on `current_user_id()`, backup role read-only, composite foreign keys to `(user_id, plan_id)` with cascade. `schedule_days` and `adjustments` are append-only (no UPDATE/DELETE privilege and no policy, both tested). `day_sessions` can change only `ended_at`; `day_reviews` only the ratings, note, outcomes and `updated_at` (column grants, tested). Bounds: note 2000 characters and 200 outcomes in the database and in Zod, reason 500, suggestion id 100 and token characters only, option 0-9.
- No new `SECURITY DEFINER` function; the convention test still requires every one to be on the reviewed list.
- Suggestion accept: the client sends `{option}` only (strict body). The suggestion is recomputed from stored reviews, logs and decisions under a `FOR NO KEY UPDATE` plan lock; an unknown or stale id is 409, an out-of-range option 422; the changed tasks are re-validated with `TaskSchema`, task and override counts are capped; preview and accept use the same function. A replayed accept returns the stored summary and changes nothing.
- IDOR: every new route loads the plan by the verified user id (404 otherwise); params are `z.uuid()` and `LocalDateSchema`. Days, reviews, briefing, open tasks and schedule routes are all behind the Terms guard (deny-by-default, tested route by route).
- Lock order: reviews and the days service use `FOR NO KEY UPDATE` and the advisory lock in the same order; FK inserts take KEY SHARE, which does not conflict with NO KEY UPDATE. After fix 2 no lock cycle remains that this review could find.
- Delete account: the key is validated (characters, length), sent only in headers, never in an error, log line or response; the request has an 8 s timeout and `redirect: 'manual'`; the id must be a UUID; a 404 from Supabase counts as done, so a retry is safe; on any Auth failure the database work rolls back (502). Tests cover a key that must not appear in logs.
- CSP: `default-src 'self'`, `script-src 'self'`, `style-src 'self'`, `connect-src` = self + API + Supabase origins, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, plus `frame-ancestors 'none'` and the other headers on Vercel and Cloudflare (kept in sync by a test). The API sends `default-src 'none'; frame-ancestors 'none'` and a hashed policy for the Swagger UI. The e2e suite fails on any CSP violation.
- Test-only seams: `__E2E__` is a build constant; `e2e-bundle.test.ts` builds the real bundle and checks the e2e code is absent (and present in the e2e build). `VITE_E2E=1` with `VITE_APP_ENV=operational` refuses to build. `E2E_NOW` is ignored when `NODE_ENV=production` (unit-tested), and both Render services use `production`. The fake sign-in only replaces the UI; the API still verifies the token.
- Day freezing: a frozen day is never scheduled again (`engineToday` skips frozen dates), and the snapshot is "as at the start of the day" for logged work (except finding 4's edge). Rollover runs under the advisory lock with `on conflict do nothing`, so two reads freeze a day once. Ending a future day or a day before the plan is 422.
- Adjustment thresholds vs 3.4: density ≥ 4 is "too much" on two consecutive **study** days; ≤ 2 is "too light"; the estimate rule fires above 25 % (integer maths, strictly greater), needs 3 completed tasks of a type, rounds the factor to 5 % and clamps it to 0.5-3.0, and skips exams and CV tasks; capacity never goes below 1 h a day and never above the study window; evidence used by an accepted suggestion is not reused, a rejected one is not offered again. Estimates are rounded to a quarter hour, never below 0.25 h.
- Week = Sunday to Saturday in the plan's zone (open tasks and the Week page agree). Trend: projected finish vs plan end date, no invented tolerance.
- Privacy: review events carry ratings and counts, never the note; the briefing is built from task metadata only and is not logged (Fastify logs no bodies); no AI call exists.
- Accessibility: dialog focus starts on Cancel, Tab cycles, Escape cancels, focus returns; status messages use `role="status"`/`aria-live`; buttons, inputs and the rating scale are at least 44 px (`min-h-11`); both charts have a `role="img"` label and a data table with a caption; axe runs on every e2e screen.
- Docs: env names in `deployments.md`, `api-auth.md`, `.env.example`, `render.yaml` and `config.ts` agree; the health endpoints (`/health` always 200 with a `database` field, `/health/ready` 503) match the code and `render.yaml`.

## Spec / data disagreements (not guessed; owner to decide)

1. **"Skipped" in the weekly Open tasks.** Spec 9 says a task skipped yesterday appears in Open tasks, marked carried over. The code treats "Skip" as "drop this task", so a skipped task is not open (finding 4). Either the test means "not done" (the day-review outcome), or Skip should keep the task in Open tasks. Which?
2. **Lesson links in the demo plan.** Spec 9 wants a specific lesson link for every course task; the demo plan has none (finding 5). Add verified lesson URLs (needs check, never invented), or accept that tasks without lessons show the course link?
3. **AI day overview in v0.2.** Section 11 lists "the AI/template day overview" in v0.2. ADR 012 ships the template only and the AI seam without an implementation (providers in v0.3). Is that the intended split?
4. **"Too much" density.** The spec scale is "too light / just right / too much" on 1-5. The code counts 4 and 5 as "too much" and 1 and 2 as "too light". Is 4 "too much"?
5. **Estimate drift "for a task type (e.g. Google PM courses)".** The example reads like a provider or course family; the code groups by task `type` (`course`, `practice`, …). Is type enough?
6. **"Overall progress for the month"** (3.1). The app shows progress for the whole plan, not the calendar month. Same thing for a one-month plan; different for longer plans.
7. **Review history on the dashboard** (3.4): currently on the review screen only (finding 9).
8. **Week boundaries.** Not in the spec; the code uses Sunday to Saturday in the plan's zone. Fine for Israel; confirm.
9. **Environment isolation vs one Supabase Auth** (finding 1): spec 9 promises R&D changes nothing in Operational, ADR 003 shares Auth. Deleting an account is the first action where this matters.

## Suggestions for v0.3

1. Decide finding 1 before anyone deletes an account on R&D. The smallest change: the Auth user is deleted only by the Operational API; R&D needs no service key.
2. One carry-over rule in the API (briefing's), used by Open tasks and the briefing; answer disagreement 1 and make `tasksAtStartOf` also reopen tasks completed or skipped on or after the date (needs a status-change date: the event log has it).
3. Estimate rule: count imported hours, and never scale an estimate below `doneHours` (findings 6, 7).
4. Put the trend (ahead/behind) in the API and show the 30-day review trend on the Week page (findings 9, 10).
5. AI providers (v0.3): add the spending cap next to `allowPaid` (12.2), keep the "no personal data" rule in one request builder with a test, and cache the overview per plan and day.
6. Make `inert` the page behind `ConfirmDialog`; render live regions empty first and fill them.
7. Run the e2e job on PRs into `rnd` and `main` only, cache the Playwright browser, and pin actions to SHAs.
8. Keep reads flat for long plans: pass only the last frozen days to the engine (finding 18).
9. Carry-overs: Turnstile and a sign-in limit, log DB errors without `detail`, one "apply time settings" endpoint with a `schedule.changed` event, production builds that fail without explicit `VITE_API_URL`.
